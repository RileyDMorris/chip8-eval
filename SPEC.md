# CHIP-8 Eval — Project Spec

You are building **CHIP-8 Eval**: a benchmark that measures how well AI coding agents can build a CHIP-8 emulator from a written spec, inside a sandbox, with no internet. It is a scaled-down version of Mechanize's GBA Eval (gbaeval.com).

Read this whole file before writing code. Work milestone by milestone (Section 9). Commit after each milestone passes its checks.

---

## 1. Goal

Produce three things:

1. **An environment**: a task prompt + sandbox + tools that let a model attempt to build a CHIP-8 emulator.
2. **A grader**: deterministic, hard-to-game scoring that compares a candidate emulator against our reference emulator on hidden tests, with partial credit by opcode family.
3. **Results**: a harness that runs several models multiple times each, and a report (tables + frame-diff images) showing where each model breaks.

Stretch: a **perturbed variant** of the spec to measure how much models rely on memorized CHIP-8 knowledge versus actually reading the spec.

## 2. Non-goals

- No sound output (timers still must work).
- No GUI is required for candidates. Everything is headless. A small viewer for demos is optional (Section 10).
- No SUPER-CHIP / XO-CHIP in v1 (possible later difficulty tier).
- Do not train models. This project evaluates them.

## 3. Hard rules (do not violate)

- **Determinism is everything.** Time is measured in executed instructions ("cycles"), never wall-clock. Randomness uses the exact LCG in Section 5.4. Same inputs → byte-identical outputs.
- **Hidden tests never enter the agent's sandbox.** The agent container gets only `tasks/<variant>/` public materials. Grading happens in a separate, fresh container.
- **No network inside agent or grading sandboxes.** Use Docker `--network none`.
- **Candidate emulators: Python 3.12 standard library only.** No pip installs inside the sandbox. This prevents installing an existing emulator and keeps grading simple.
- **Secrets**: model API keys come from environment variables in `.env` (gitignored). Never commit keys. Never pass keys into the agent sandbox; the harness calls the model API from the host.
- **Keep the reference emulator separate** from anything the agent can see. The agent must never see `reference/`.
- **No third-party ROMs committed to the repo.** All test programs are generated by our own ROM builder (Section 6). Optional external test ROMs may be fetched by a script at setup time only after checking their license.

## 5. Canonical machine spec (source of truth for `machine/canonical.md`)

This section defines exactly what "correct" means. The reference emulator must implement it exactly, and `machine/canonical.md` must restate it clearly for the agent.

### 5.1 Machine state

- Memory: 4096 bytes, addresses `0x000–0xFFF`. All memory access is masked with `& 0xFFF`.
- Program loaded at `0x200`. `PC` starts at `0x200`.
- Font: 16 sprites (`0`–`F`), 5 bytes each, stored at `0x050–0x09F`, standard CHIP-8 font bytes.
- Registers: `V0`–`VF` (8-bit). `I` (16-bit, wraps at `0xFFFF`). `PC` (12-bit effective). Delay timer `DT`, sound timer `ST` (8-bit).
- Stack: 16 entries of return addresses. `SP` starts at 0.
- Display: 64×32 monochrome, all pixels off at start.
- Keypad: 16 keys, `0x0`–`0xF`.

### 5.2 Timing

- One **cycle** = fetch, decode, execute exactly one instruction.
- After executing cycle number `c` (1-indexed), if `c % 10 == 0`, decrement `DT` and `ST` by 1 if they are > 0.
- Instructions are 2 bytes, big-endian. `PC += 2` after fetch, before execute.

### 5.3 Instructions (35)

| Opcode | Meaning |
|---|---|
| `0NNN` | SYS: no-op |
| `00E0` | Clear display |
| `00EE` | Return: pop PC from stack |
| `1NNN` | Jump to NNN |
| `2NNN` | Call: push PC, jump to NNN |
| `3XNN` | Skip next if VX == NN |
| `4XNN` | Skip next if VX != NN |
| `5XY0` | Skip next if VX == VY |
| `6XNN` | VX = NN |
| `7XNN` | VX = (VX + NN) & 0xFF; VF unchanged |
| `8XY0` | VX = VY |
| `8XY1` | VX \|= VY; VF unchanged |
| `8XY2` | VX &= VY; VF unchanged |
| `8XY3` | VX ^= VY; VF unchanged |
| `8XY4` | VX = (VX + VY) & 0xFF; then VF = 1 if carry else 0 |
| `8XY5` | VX = (VX − VY) & 0xFF; then VF = 1 if original VX >= original VY else 0 |
| `8XY6` | VX = VX >> 1 (VY ignored); then VF = shifted-out bit |
| `8XY7` | VX = (VY − VX) & 0xFF; then VF = 1 if original VY >= original VX else 0 |
| `8XYE` | VX = (VX << 1) & 0xFF (VY ignored); then VF = shifted-out bit |
| `9XY0` | Skip next if VX != VY |
| `ANNN` | I = NNN |
| `BNNN` | Jump to NNN + V0 |
| `CXNN` | VX = rand() & NN (Section 5.4) |
| `DXYN` | Draw (Section 5.5) |
| `EX9E` | Skip next if key VX & 0xF is down |
| `EXA1` | Skip next if key VX & 0xF is up |
| `FX07` | VX = DT |
| `FX0A` | Wait for key (Section 5.6) |
| `FX15` | DT = VX |
| `FX18` | ST = VX |
| `FX1E` | I = (I + VX) & 0xFFFF; VF unchanged |
| `FX29` | I = 0x050 + 5 × (VX & 0xF) |
| `FX33` | Store BCD of VX at I, I+1, I+2 |
| `FX55` | Store V0..VX at I..I+X; I unchanged |
| `FX65` | Load V0..VX from I..I+X; I unchanged |

"Then VF = ..." means the flag is written **after** the result, so if X == F the flag wins.

Any opcode not in this table is **invalid**: the emulator halts (Section 5.7).

### 5.4 Random numbers

LCG with 31-bit state. Initial `state = seed` (default seed 1).
Each `rand()` call: `state = (state * 1103515245 + 12345) % 2**31`, returns `(state >> 16) & 0xFF`.

### 5.5 Drawing (`DXYN`)

- Start position: `x0 = VX % 64`, `y0 = VY % 32` (start wraps).
- Draw N rows (sprite bytes from `I`..`I+N−1`), MSB = leftmost pixel.
- Pixels beyond the right or bottom edge are **clipped**, not wrapped.
- Each sprite pixel that is 1 XORs the display pixel.
- VF = 1 if any pixel turned from on to off, else 0.

### 5.6 Key wait (`FX0A`)

If any key is currently down, VX = the lowest-numbered down key and execution continues. If no key is down, the instruction repeats (PC moves back by 2). Cycles keep counting and timers keep ticking while waiting.

### 5.7 CLI contract (what every candidate emulator must implement)

```
python emulator.py --rom PATH --cycles N [--keys KEYS.json] [--seed S] [--frames-at C1,C2,...]
```

- Runs exactly N cycles (or until halt) and prints **one JSON object** to stdout:

```json
{
  "halted": false,
  "halt_reason": null,
  "cycles_run": 1000,
  "state": { "v": [16 ints], "i": 0, "pc": 512, "sp": 0, "stack": [ints], "dt": 0, "st": 0 },
  "frames": { "<cycle>": ["<64 chars of 0/1>", "... 32 rows"] },
  "final_frame": ["... 32 rows of 64 chars"]
}
```

- `KEYS.json`: list of `{"cycle": int, "key": int, "down": bool}` events, applied **before** executing that cycle.
- `--frames-at`: dump the display after executing each listed cycle.
- Halt conditions: invalid opcode, stack overflow (push with 16 entries), stack underflow (return with 0 entries), PC reaching `0x1000`. On halt: stop, set `halted: true`, `halt_reason` to one of `"invalid_opcode"`, `"stack_overflow"`, `"stack_underflow"`, `"pc_out_of_bounds"`, and still print the JSON with the state at halt. `"stack"` lists entries bottom-to-top.

## 6. Components

### 6.1 Reference emulator (`reference/`)

- Implements Sections 5.1–5.7 exactly, plus the variant via a config object (Section 8).
- Validated by `tests/test_reference.py`: at least one hand-written test per opcode **written from the spec text, not from the implementation**, including edge cases (X == F flag ordering, clipping, start wrap, BCD of 0 and 255, timer ticks at cycle multiples of 10, FX0A repeat behavior, every halt reason).

### 6.2 ROM builder and test generation (`romgen/`)

- `builder.py`: Python DSL that emits bytes, e.g. `LD(V0, 0x12)`, `ADD(V1, V2)`, `DRW(V0, V1, 5)`, labels for jumps.
- **Unit tests** (`unit_tests.py`): for each opcode, 2–4 small programs that set up registers, run the instruction, and end in a tight loop (`1NNN` to self). Graded on final `state` plus `final_frame`. Target: ~100 unit tests total. Tag each with its opcode family:
  `flow` (00EE, 1NNN, 2NNN, BNNN, skips), `alu` (8XY*), `load` (6XNN, 7XNN, ANNN, FX1E, FX29), `memory` (FX33, FX55, FX65), `display` (00E0, DXYN), `timers` (FX07, FX15, FX18), `input` (EX9E, EXA1, FX0A), `random` (CXNN), `halt` (invalid opcode, stack errors).
- **Program tests** (`programs.py`): ~15 longer programs (sprite animation with collision, a BCD score counter rendered with the font, a timer-driven loop, a key-driven menu, a random-pattern generator with fixed seed, nested calls). Each has 3–6 frame checkpoints plus scripted key events.
- Generate golden outputs by running the reference emulator. Store under `tests_data/hidden/<variant>/`.
- Public set (`tests_data/public/<variant>/`): 6 unit tests + 2 program tests, with golden outputs, drawn from a **separate seed/selection** so they never duplicate hidden tests.

### 6.3 Agent harness (`harness/`)

- Minimal tool-using loop in `agent_loop.py`, model-agnostic, using an OpenAI-compatible chat API with tool calling (OpenRouter or direct provider APIs). Keys from `.env`.
- Tools available to the agent, executed inside its container:
  - `bash(command)`: run a shell command in `/workspace` (timeout 60s, output truncated to 10k chars).
  - `read_file(path)`, `write_file(path, content)`: limited to `/workspace`.
  - `submit()`: ends the episode.
- The agent container gets `tasks/<variant>/` copied into `/workspace`: `prompt.md`, `machine_spec.md`, `public_tests/`, and `run_public_tests.py` (a self-check script that runs `emulator.py` on the public tests and prints pass/fail).
- Budgets (configurable in `models.yaml`): max 150 tool calls, max 2 hours wall-clock, max token/$ budget per run. When any budget is hit, the episode ends and whatever is in `/workspace/emulator.py` is graded.
- Log every message and tool call to `results/runs/<run_id>/transcript.jsonl`. Save the final `emulator.py`.
- Containers: non-root user, `--network none`, CPU/memory limits, removed after the run.

### 6.4 Grader (`grader/`)

- Copies only the candidate's `emulator.py` into a fresh grader container, then runs every hidden test with a 10s per-test timeout.
- Compares candidate output to golden output:
  - Unit test passes if `halted`, `halt_reason`, every `state` field, and `final_frame` match exactly.
  - Program test: each checkpoint frame either matches exactly or not; also record per-checkpoint pixel accuracy (`matching_pixels / 2048`).
  - Malformed JSON, crash, or timeout = test failed, recorded with reason.
- Writes `scores.json` with per-test results, per-family pass rates, and the overall score.

## 7. Scoring

- **Unit score** = fraction of unit tests passed (also reported per family).
- **Program score** = fraction of program checkpoints matched exactly.
- **Robustness score** = fraction of all tests that produced valid JSON within the timeout.
- **Overall** = 0.5 × unit + 0.4 × program + 0.1 × robustness.
- Per model: run K = 3 attempts; report the mean and min/max of each score.

### 7.1 Grader validation (required before any model runs)

`grader/mutants.py` creates broken copies of the reference emulator, each with one deliberate bug (for example: 8XY5 flag uses `>` instead of `>=`; flag written before result; sprites wrap instead of clip; FX55 increments I; timers tick every 9 cycles; CXNN ignores seed). For each mutant, assert:

1. The reference scores 100%.
2. Every mutant scores below 100%.
3. Each mutant loses points in the opcode family it broke.

This proves the grader detects real bugs. Include the mutant results in the report.

## 8. Variant spec (stretch, M5)

`machine/variant_v.md` is the canonical spec with deliberate changes. The reference supports both through a config object; golden outputs are generated separately per variant. Initial changes:

1. Font stored at `0x000`; `FX29` sets `I = 5 × (VX & 0xF)`.
2. `3XNN` skips if **not** equal; `4XNN` skips if equal (swapped).
3. `7XNN` sets VF = 1 on overflow, else 0.
4. Timers tick every **8** cycles.
5. New opcode `5XY1`: `product = VX × VY`; VX = product & 0xFF; then VF = product >> 8.

The prompt must say clearly that this is a modified CHIP-8 and the spec overrides prior knowledge. The headline metric is the **memorization gap**: canonical score minus variant score, per model, and which changes each model got wrong.

## 9. Milestones

Each milestone ends with its checks passing and a commit.

- **M0: Reference emulator.** Repo scaffold, `reference/`, CLI contract, `tests/test_reference.py`. Check: all reference tests pass; the same run twice gives byte-identical output.
- **M1: Test generation.** `romgen/`, ~100 unit tests, ~15 program tests, public/hidden split, goldens. Check: every hidden test passes against the reference; no public test duplicates a hidden test.
- **M2: Grader + validation.** `grader/`, `mutants.py`, Section 7.1 checks. Check: reference = 100%; every mutant < 100% in the right family.
- **M3: Sandbox + agent loop.** Docker images, `sandbox.py`, `agent_loop.py`, one model end to end on the canonical task. Check: a full run produces transcript, `emulator.py`, and `scores.json`; `--network none` verified with a test that tries to reach the internet from the agent container.
- **M4: Full canonical eval.** 3 models × 3 runs. `make_report.py` produces `REPORT.md` with an overall table, a per-family heatmap table, and frame-diff PNGs (candidate / reference / diff side by side) for the most interesting failures.
- **M5: Variant.** `variant_v` spec, reference config, goldens, and the same 3 × 3 runs. Report the memorization gap.
- **M6: Writeup.** `README.md`: what the eval measures, design decisions (determinism, hidden tests, grader validation), results, surprising failures, limitations, and how to run it.

## 10. Optional extensions (after M6)

- Run agent sandboxes as Kubernetes Jobs on the local cluster instead of plain Docker, with parallelism.
- A small viewer (HTML canvas or pygame) to replay any candidate's frames next to the reference.
- A "vendor agent" track: run off-the-shelf coding agents headless in the same sandbox and compare against the minimal harness, to separate model ability from scaffolding.
- SUPER-CHIP tier for more difficulty if models saturate the canonical task.

## 11. Working agreements for Claude Code

- Write tests before or alongside code; run them before each commit.
- Small commits with clear messages, one milestone at a time. Do not start a milestone until the previous one's checks pass.
- When the spec is ambiguous, stop and ask rather than guessing. Record decisions in a `DECISIONS.md` log.
- Never weaken a check to make it pass. If a check seems wrong, flag it.
